# DeployHub architecture

Independent approval is retired. Production is a target classification, not an approval gate. Retained `requires_approval` fields participate only in immutable candidate and issued-token fingerprint compatibility; new settings normalize the retired flag to false. Approval records remain historical. Existing `awaiting_approval` requests never auto-run: the original requester must reconfirm with current grants, MFA, digest, expiry and configuration checks. Immediate reconfirmation excludes only its own existing reservation and atomically enqueues once; schedules must be reconfirmed before their due time. Approval/rejection endpoints are removed, and `/approvals` redirects to filtered activity. No data migration or automatic enqueue is performed.

## Application boundaries

Laravel 12, Inertia 2, Vue 3 and TypeScript serve a session-authenticated dashboard. MySQL stores records, encrypted credentials, sessions, cache locks and queue jobs. phpseclib 3 is the only production outbound SSH transport. The local test transport exists under `tests/Support` and cannot be selected through application configuration or the UI.

The application presents one active workspace per user. Each project has one environment, enforced by a unique project ID. The additive migration separates previous multi-environment projects, retaining environment IDs, grants and immutable deployment records and copying project assignments. Project/environment soft deletion retains authorized history reads, blocks new actions and releases the unique active registered_path. Active reservations or repository locks prevent deletion. Access combines active membership, role, project assignment, server assignment and environment grants. Policies protect actions and every deployment/log read. HTTP middleware checks MFA and admin membership; workers repeat requester authorization from fresh records.

## Data and credential handling

The Streamable HTTP `/mcp/deployhub` endpoint uses `laravel/mcp` and exposes target discovery, exact-commit preview, confirmation and status. `AutomationGrant` stores a hashed bearer token bound to one user/workspace, with expiry, revocation and an identity fingerprint. `automation_grant_targets` is the authoritative explicit allowlist of 1–100 targets, each with its issued target fingerprint. New projects are not enrolled automatically, and changing the allowlist requires new issuance. Issuance requires enrolled and session-verified MFA, the current password and explicit rights to every selected target in the same workspace; failure rejects the entire request. Bearer calls require current deployment rights and matching password/MFA/target identity; browser sessions are not an authentication substitute. Discovery filters unusable targets; a changed/revoked target cannot execute or expose its logs while unaffected targets remain usable. Token/identity revocation affects all targets. All authorized targets, including production, enter the queue after requester confirmation without independent approval. See [AI deployment access](AI_DEPLOYMENTS.md).

The forward target-scope migration transfers stored fingerprints into explicit target rows without changing hashes, grant IDs or candidate snapshots/digests, then removes `automation_grants.environment_id` and `target_fingerprint`. There is no single-target relation or request-format fallback: issuance uses `environment_ids`, and authorization uses the target rows exclusively. Missing allowlist entries fail closed. Pivot fingerprints are hidden from model serialization and are not returned by tools or controller projections. Downgrade would collapse multi-target scopes, so this migration requires backup restoration with matching code rather than an automatic down migration.

Web and MCP confirmation share `DeploymentConfirmation`, preserving the environment reservation and primary-database enqueue transaction. Automation previews freeze their grant ID inside candidate integrity. `CandidateService::validate` reconstructs this metadata and validates the grant before every worker step. Revocation/expiry or authorization changes stop subsequent steps without undoing completed commands. MCP callers cannot access another grant's candidates/logs, change configuration, pass shell commands or schedule deployments.

`ServerCredential` uses Laravel encrypted casts and hides both key and passphrase. The connection service verifies the peer fingerprint before decrypting keys or authenticating. Registration validates the key; neither returned props nor job payloads contain credential material. Credential rotation and peer changes invalidate existing deployment digests.

An administrator can explicitly pin the first discovered key using first-use trust, or attest to independent verification. First-use trust is available only without an existing pin; replacing a saved key requires independent verification. Discovery is bound to the session, host, port, account, credential version and existing pin, expires after ten minutes, and is checked against a second discovery. A locked transaction rechecks that context before saving trust, invalidating preflight and recording the chosen method in the audit log. Connections always enforce the saved pin; no connection automatically enrolls or replaces a host key.

The candidate snapshot contains configuration and enabled hook scripts, not credential-vault material. Scripts should reference remote environment variables rather than embed secrets. Its digest includes requester, exact starting and target commits, server identity, credential version, path/ref, production classification and retained legacy approval metadata, pipeline version/options, enabled scripts and any reviewed working-tree digest. Digest construction recursively sorts JSON object keys while preserving array order and scalar types. This tolerates MySQL JSON key normalization without ignoring changed hook order, values or identity. Existing candidates can validate their original ordered digest against an unchanged reconstructed snapshot; saved candidate/digest records are not rewritten. Candidate columns are immutable through Eloquent. State, timestamps, worker token, cancellation and result fields are separately mutable.

`AuditLog` rejects updates/deletes through Eloquent. Audit rows reference actor IDs and retain safe metadata; this is application-level append-only behavior, not cryptographic tamper evidence against a database administrator.

## Repository and execution lifecycle

1. A policy-authorized inspection acquires the environment lock. Explicit Refresh always inspects remotely; Review can reuse a successful result from the last 120 seconds if its format/version and configuration digest still match and no target reservation is active. Configuration/credential changes, failed results and expired cache force fresh inspection. Recovery always inspects remotely.
2. The SSH service pins the peer and authenticates. InspectionBatch groups repository identity checks into one SSH exec and fetch/target/ancestry/commit checks into another. Random framed fields retain binary output and each command exit status. Incomplete/malformed results are rejected. Bounds apply to the whole batch; no remote temporary files are created.
3. Git plumbing checks canonical root, exact origin and the configured non-detached branch. Local changes are listed as local_changes without a blanket clean-tree requirement. Enabled Pre hooks additionally freeze tracked worktree/index diffs and untracked content hashes in at most two additional SSH batches. Raw file contents are not persisted; bounded SSH output and a 200-file limit apply to Pre-hook review.
4. Fetch retrieves the configured branch. Ancestry, incoming commits and full SHA-1 IDs are inspected from completed commands.
5. A deployment preview freezes configuration, commits and a one-hour expiry. A single-time schedule additionally freezes its UTC time and display timezone, with expiry one hour after the chosen time. Scheduling is limited to a future time within 30 days. No Git update occurs during preview.
6. Immediate requester confirmation reserves the environment and atomically inserts a database job, including production. Scheduled confirmation enters `scheduled` without reserving the target or creating a job; confirmation must finish before the due time.

When the requester chooses Schedule on a normal review, confirmation validates the reviewed digest, expiry, fresh grants and configuration, then creates a new candidate using exactly that review's base/target, preflight and scripts with the chosen time/timezone. No second SSH inspection occurs and existing immutable fields are never rewritten. Under the same environment/source row locks and transaction, the source review is marked cancelled and the new candidate is confirmed. A source-derived idempotency key makes identical retries return that request; conflicting times are rejected. Creation/cancellation/confirmation roll back together on failure. Requester confirmation binds the new time-inclusive digest.
7. A worker acquires the lock and atomically claims `queued → running`, storing a unique execution token.
8. Authorization, digest and Git state are rechecked. Workers always fetch remotely, bypassing the preview cache, but skip commit-list/count queries that the worker does not use. Each remote exec, including an inspection batch, records a heartbeat and checks execution ownership.
9. The worker verifies the frozen worktree digest before enabled Pre hooks. Ordered Pre hooks run, then one identity/ref batch checks unchanged reviewed base/target without repeating fetch or commit history. A Pre hook that changes HEAD requires reconciliation. Git merges only the reviewed SHA with --ff-only --no-overwrite-ignore; unrelated local changes remain and overlapping changes fail at merge. Built-in Git commands disable automatic hooks and local/ext transports.
10. Ordered Post hooks run, followed by final HEAD verification. Built-in options share enabled/phase/order controls with custom hooks; health is Post only and defaults last. Hard reset defaults disabled in Pre and uses typed git reset --hard HEAD. Built-in names/scripts are canonicalized on save and execute through CommandBuilder. Migration moves existing pipeline selections into workflow options; immutable legacy candidates remain readable. Configuration permits 26 entries, including six defaults. Custom hooks use separate POSIX sh -e sessions rooted in the repository, with LF-normalized, quoted scripts frozen in the digest. Sessions do not share exports or directory changes. Every selected step is mandatory; selected health checks require 2xx and final HEAD must match the target.
11. Completed step output is sanitized before saving. Active execution polling runs every 2.5 seconds; pending scheduled reviews/plans poll every 15 seconds with normal session/policy protection and no-store responses. Poll responses explicitly load target/project metadata and the server ID/name, matching the detail page regardless of which relations authorization loaded. The page tolerates missing server metadata and stops polling after displaying a terminal state.

Only one active request can reserve an environment through a unique nullable active-environment column. A unique (server_id, registered_path) prevents duplicate active directories; archived registrations retain their original path but clear registered_path. Database locks are shared by HTTP/workers. Lock lease is 1,200 seconds, command timeout 120 seconds, executor budget 900 seconds, queue timeout 960 seconds and retry-after 1,200 seconds. Enqueue remains tied to the primary database; changing queue driver requires an outbox/admission design.

Every minute, `deployhub:dispatch-scheduled` records a 90-second scheduler heartbeat and scans up to 100 due plans. Under the same environment cache lock and a database transaction locking the environment/candidate, it rechecks requester membership, explicit grants, MFA, the immutable digest and configuration. Missing requester confirmation at the due time expires the plan. Changed authorization/configuration fails it without SSH. Active reservations, including unknown quarantine, make a plan wait within its one-hour execution window. An eligible plan changes `scheduled → queued` and gains its unique reservation in the same transaction as database job creation. Cancellation, archive and repeated dispatch cannot queue it again. Queue insertion failure rolls back both state and reservation.

Workers reject execution before the scheduled time and perform the usual fresh exact-base/target inspection once due; a new branch tip or changed checkout requires a new review rather than silently deploying newer code. If the machine was offline, a confirmed plan can catch up within one hour; later plans expire. Scheduled time is an earliest dispatch time, not a guarantee of an exact second. The scheduler never retries a partially executed workflow. Deleting an otherwise idle project expires its pending scheduled records while retaining history.

## Failure and recovery

Known mandatory-stage failures are `failed`, with completed stages and `code_updated` preserved. Network loss or unexpected worker faults are `unknown`, retain the environment reservation and require reconciliation. A separate worker token prevents a failed duplicate job from marking another worker's execution unknown.

A failed deployment with updated code can create a separate recovery candidate. Its digest includes the source deployment ID, fresh configuration, requester and exact SHA. Fresh preflight requires HEAD and fetched origin to equal the failed target; the recovery pipeline skips fast-forward and reruns every selected typed step. Review, expiry, explicit grants, MFA, requester confirmation and worker revalidation apply to recovery. The source record remains unchanged. Unknown state cannot enter recovery without the separate reconciliation process.

Project history and dashboard recent deployments exclude expired records and awaiting requests whose expiry or scheduled confirmation deadline has passed, even before reconciliation runs. Latest project summaries apply the same exclusion before selecting the newest admitted record. Activity retains the complete authorized history and applies search/state filters on the server; history pagination orders by creation time and ID. All queries remain limited to visible environments. Environment-name validation mirrors the per-project database constraint, with project row locks serializing names on create/edit. Server reassignment identifies members with view grants who lack the new server assignment, requires explicit transfer and audits the transferred IDs in the same transaction as the configuration update.

The scheduler expires unexecuted candidates and quarantines running jobs whose heartbeats exceed the lock lease. It never automatically declares remote success or releases unknown quarantine. Administrator reconciliation requires explicit process-stopped attestation, a safe repository inspection and an audit reason. It produces `reconciled`, not `succeeded`.

There is no automatic retry of partial workflows. Recovery uses fresh review and replays enabled Pre/Post options and scripts. An up-to-date checkout can prepare a candidate with enabled workflow entries. There is no code/data/shared-file rollback. Local changes retained during deployment mean the working tree may differ from committed contents even when HEAD matches the target.

## Browser/UI

`HubLayout` provides responsive navigation, accessible controls, dark/light themes and role-aware navigation. Tables become labelled cards at small widths. Registry forms, deployment reviews and console states reflect backend capabilities. No fabricated connection or repository readiness is displayed: new targets are unverified/unknown until actually inspected.

Navigation groups deployment work separately from administration. Overview links to authorized projects, failed deployments in the last 30 days, unexpired scheduled plans. Project summaries use separate one-of-many relations for the latest admitted deployment (excluding drafts/cancelled previews) and last success across all history, independent of the current history page. Both relations select only summary columns and requester ID/name, never snapshots, logs, credentials or email. Existing project/environment permissions still govern serialization. Last success is historical evidence, not the current live version; a later failure may have updated code. Repository HEAD/incoming counts are explicitly from the last inspection. Copy project resides in collapsed Repository details.

Review uses a desktop information/confirmation split that stacks on mobile, with an anchor to the confirmation form. Full commit/path and historical approval metadata and execution order are collapsed. After review, the workflow card itself collapses to prioritize execution results. Execution phases derive from planned step types and actual recorded states; no percentage or implied successful future stage is fabricated. Steps display recorded start/finish-based duration, highlight running work, and collapse successful output while opening failed/unknown output. Unknown timestamps are labelled Status recorded, not proof that remote processes finished. One polling chain captures the deployment ID so an older response cannot overwrite a replacement candidate. Navigation/unmount clears polling, elapsed-clock and feedback timers; expiry updates from the same one-second clock. Command output remains buffered.

Workflow editors group actions by Pre/Post; individual entries do not repeat the phase selector. Command/script details default collapsed, newly added custom hooks open for editing, and server validation errors reopen the relevant editor. Reviewed scripts are also collapsed by phase. Prepare deployment opens one review/confirmation form with Deploy now selected by default. Schedule reveals a browser-local date/time input and dispatcher-heartbeat guidance, sending an ISO UTC instant and IANA timezone with confirmation. Changing timing clears the review checkbox. Legacy pending approval requests require explicit reconfirmation by the requester before execution. Scheduled records and dates appear in existing paginated deployment history/activity; there is no Schedule tab or additional page. The empty console is hidden until confirmation or execution.

Step output is command-buffered rather than raw-streamed to prevent disclosure across chunk boundaries. The sanitizer limits persisted output to 32 KiB per step; SSH collection is bounded at 128 KiB per command. Health response bodies are discarded entirely.
