# DeployHub review — 9 October 2026

This is the initial review record. Its four findings are addressed in the [repair validation](FIXES_2026-10-09.md); the original observations are retained here for reference.

One review round of the current working tree. Overall assessment: **7.5/10 as an internal deployment MVP**. Application code was not changed.

## Confirmed findings

### P1 — Partial deployment failure has no same-commit recovery flow

`app/Services/Deployment/CandidateService.php:66` rejects previews with zero incoming commits. Once fast-forward succeeds, a failure in Composer, cache operations, or health checks leaves HEAD at the target SHA. Fixing the underlying cause and preparing a new deployment then fails with "Already up to date". The deployment detail offers no retry/resume action for failed jobs.

Reproduced with a successful fast-forward followed by a failing health check, then a healthy remote and a fresh preview request. The preview still fails. Recovery requires manual remote work or another upstream commit.

Suggested repair: add an explicitly reviewed recovery candidate for the same SHA, with fresh preflight, permissions, configuration and independent approval checks. Make completed and remaining steps clear; avoid blindly replaying commands.

### P2 — Pending approvals can disappear from the approvals page

`app/Http/Controllers/HubController.php:32` loads the latest 50 deployments of every state. `resources/js/Pages/Hub/Index.vue` filters that already-truncated list to pending approvals in the browser. A pending request with 50 newer previews/jobs disappears, while the dashboard's pending count still reports it.

Reproduced with one pending production request and 50 newer unconfirmed previews. The `/approvals` response reports `stats.approvals = 1`, but none of its 50 deployments is pending approval. The UI consequently shows "No pending approvals". Activity and environment history also have fixed limits without pagination.

Suggested repair: filter pending, unexpired requests on the server before pagination, and paginate activity/history independently.

### P2 — Duplicate environment names produce a database exception

`app/Http/Controllers/ProjectController.php:25` validates the remote path's uniqueness but not environment-name uniqueness within a project. The database enforces `(project_id, name)` uniqueness in `database/migrations/2026_10_08_000001_create_deployhub_tables.php:88`.

Reproduced by adding another "Staging" environment to the same project at a distinct remote path. The request throws `QueryException` instead of returning a field validation message. The same gap applies when renaming an environment to another existing name.

Suggested repair: validate names scoped to the project, ignoring the current environment when updating; handle concurrent duplicate submissions gracefully.

### P2 — Changing an environment's server silently drops member access

`app/Http/Controllers/ProjectController.php:107` updates `server_id`, leaving existing environment permissions intact. `app/Services/Access.php` also requires membership of the selected server, so users granted only the old server lose access despite their environment permission still showing `can_view = true`.

Reproduced by granting a developer access, changing the environment to another workspace server, and requesting its detail page as that developer: HTTP 403. Administrators remain able to observe the environment, which can conceal the issue during setup.

Suggested repair: warn about affected members before changing the server and provide a deliberate access regrant flow. Any grant on the new server should respect its separate permission boundary.
